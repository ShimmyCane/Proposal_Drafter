# Proposal Consideration Framework

## Purpose

This file turns a project brief into a clear proposal scope. It supports three tasks:

1. identify the actual project type and service path,
2. forecast the real scope, schedule, and deliverables,
3. translate that into a proposal with correct fee logic and exclusions.

The Gardena example demonstrates why this matters: a generic design proposal is not the same as a limited permit-set proposal for a builder or developer.

## 2. Scope decision logic

### Prompt-first selection
Before drafting, ask the client or project lead:
- [ ] Full design project
- [ ] Permit-set / limited-service project
- [ ] Planning / entitlement support project
- [ ] Hybrid project

If the project type is unclear, do not assume the default. Prompt the user before writing the proposal.

### A. What kind of work is this?
Choose the primary logic:
- [ ] Existing condition / as-built based work
- [ ] Limited permit-set / builder's set work
- [ ] Design-led work
- [ ] Permit / RTI / resubmission work
- [ ] Entitlement / planning support work
- [ ] Change of use / code-driven work
- [ ] Tenant improvement work
- [ ] New build / addition / ADU work

### B. What is the likely project path?
- [ ] Site and zoning review
- [ ] Planning / entitlement support
- [ ] Design coordination / concept work
- [ ] Design development
- [ ] Construction documents
- [ ] Permit submission / plan check support
- [ ] RTI / approval support
- [ ] Construction administration

### C. What is the likely starting point?
- [ ] Existing drawings available
- [ ] Similar unit plans available
- [ ] Sketch / rough concept available
- [ ] No drawings, need to develop from scratch
- [ ] Existing building requires as-builts
- [ ] Existing building requires site evaluation

## 3. Project-specific task checklist

### Site and planning review
- [ ] Review site context and parcel logic
- [ ] Identify planning or entitlement path
- [ ] Confirm whether SB 684 / SB 1123 / or other local procedures apply
- [ ] Review lot split or subdivision assumptions
- [ ] Confirm site constraints, setbacks, and parking logic

### Design and coordination
- [ ] Coordinate with client and design team
- [ ] Review mirrored or repeated unit assumptions
- [ ] Confirm unit count, massing, and basic programming
- [ ] Prepare conceptual or schematic adjustments if needed
- [ ] Coordinate with civil, landscape, and structural consultants

### Documentation and permit drawings
- [ ] Prepare architectural permit set
- [ ] Prepare site plans, floor plans, elevations, sections, details, and schedules
- [ ] Prepare building code and permit support notes
- [ ] Submit with agency coordination and plan check support
- [ ] Revise drawings for plan check comments and RTI

### Deferred or excluded items
- [ ] Fire sprinklers / deferred submittal
- [ ] Structural engineering
- [ ] MEP engineering
- [ ] Civil and landscape design
- [ ] Survey / soils / hydrant flow / geotechnical reports
- [ ] Plotting and reproduction charges
- [ ] Construction administration

## 7. Questions to resolve before drafting

Before drafting the proposal, confirm:
- Is the work permit-led, design-led, or both?
- Are the plans based on existing precedent, mirrored duplex plans, or a new design?
- Is there a subdivision or lot-split process involved?
- Which consultants are being provided by the owner versus the architect?
- Are fire sprinklers, plotting, or deferred submittals part of the fee?
- Is a plan check or RTI phase included in the base scope?
- Is construction administration excluded or intentionally added?
- What assumptions are being made about finish selection, owner decisions, and consultant timing?

---

## 8. Proposal drafting notes

When drafting the proposal, make sure to:
- state the project type clearly,
- define the real base scope,
- separate included work from additional services,
- avoid generic design-phase language when the project is permit-led,
- note schedule assumptions and dependencies,
- use a professional and persuasive tone,
- keep the proposal welcoming while protecting the scope,
- confirm that the actual project facts match the assumptions in the proposal.

---

## 9. Example of a realistic project-specific clause

For a limited-service permit package, a better base language is:

"This proposal provides limited architectural services for the preparation of a builder's permit set, including site and zoning review, planning support coordination, architectural drawing preparation, and agency plan check support. Related consultant disciplines, deferred submittal systems, fire sprinkler design, plotting, and construction administration are excluded unless separately identified in writing."

This reads more like the actual Gardena proposal than the generic broad-scope language used in a more open-ended design proposal.

### Starter block: small-lot subdivision / duplex permit package
- Project path: [Permit-led / limited service]
- Project type: [Small-lot subdivision / duplex / permit set]
- Base scope: [site and zoning review, permit drawings, agency coordination, RTI support]
- Exclusions: [structural, MEP, civil, landscape, plotting, construction admin, deferred submittals unless specified]
- Pricing: [fixed fee + milestone billing]

## 10. AI comparison checklist

Before accepting or revising any AI-generated proposal, confirm:
- [ ] The project path matches the actual client request.
- [ ] The proposal is not assuming broad design scope when the client asked for a limited permit package.
- [ ] The fee aligns with the actual deliverables, assumptions, and milestone structure.
- [ ] Consultant responsibilities are clearly separated from owner responsibilities.
- [ ] Exclusions and deferred submittals align with the real project conditions.
- [ ] The language has been compared to the client-authored narrative before finalization.
